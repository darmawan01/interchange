# tools — the codegen plugins

Two protoc plugins and the small runtime they generate against.

| Path | What it is |
| --- | --- |
| `cmd/protoc-gen-bus` | emits the `*interchange.ServiceDesc`, the server interface, a typed bus client and a registration helper |
| `cmd/protoc-gen-cli` | emits a Cobra command tree from `(interchange.cli.v1.command)` |
| `clisupport` | the runtime half of the CLI: `Invoker`, field parsing, JSON output, `Coverage` |
| `api/`, `gen/go/` | this module's own annotation, `(command)` = 50004, and its generated Go |

## protoc-gen-bus

Output: `<dir>/<pkg>bus/<proto>_bus.pb.go`, package `<pkg>bus` — a sub-package, so a service's
generated code and its message types never collide. Per service:

- **`New<Service>Desc() *interchange.ServiceDesc`** — the one artefact that makes the HTTP binding
  and the bus binding serve the same handler. Each `MethodDesc` carries the procedure, the message
  factories, the type-asserting handler closure, the resolved transports, the group, `Idempotent`
  (`idempotency_level = NO_SIDE_EFFECTS`), `Internal` (the `(internal)` annotation) and the
  `protoreflect.MethodDescriptor`, looked up **by name** so inserting an RPC cannot silently
  repoint the descriptor an optional module reads its own annotation off.
- **`<Service>Handler`** — the server interface. One implementation serves every road.
- **`Register<Service>(r, impl, chain)`** — `r` is an *anonymous* interface with core's
  `Register(sd, impl, chain) error` method. Both `*interchange.Registry` and `*rpc.Binding`
  satisfy it. See "Seams" below.
- **`New<Service>BusClient(*engine.Client, ...)`** — only for services with a method on
  `TRANSPORT_BUS`, `_MQTT` or `_WS`, and only those methods get client methods: a generated call to
  a procedure nothing subscribes to is a timeout wearing a confident signature.

It does **not** emit subscribers. `engine.Server` subscribes from the registry, so the ServiceDesc
already is the subscriber; generating one would be a second source of truth for the same fan-out.

### Do generated bus clients block? (docs/08)

Both, deliberately. `GetItem(ctx, req)` blocks — and that is the trap the open question names, a
signature that looks local over a call that is not. So every method also has
`GetItemWithin(ctx, timeout, req)`, which puts the network deadline in the signature where a caller
cannot miss it, and `With<Service>Timeout` sets a default for the plain form.

### Transports resolution

| Annotation | Roads | Group |
| --- | --- | --- |
| per-method `(transports)` | its `on` | its `group` |
| service `(service_transports)` only | its `on` | its `group` |
| neither | `TRANSPORT_RPC, TRANSPORT_REST` | none |

The per-method annotation **replaces** the service default entirely, group included — a reviewer
reads one annotation, not two composed. The emitted list is sorted by enum value and deduped: it is
a set, and generated bytes must not depend on the order someone happened to type.

Refused, with the source location: a streaming RPC (interchange is unary only), an annotation that
names no road (`(transports) = {group: "x"}` reads both as "only change the group" and "expose on
nothing"; guessing is how an internal RPC reaches a public bus), and `TRANSPORT_UNSPECIFIED`.

## protoc-gen-cli

Output: `<dir>/<pkg>cli/<proto>_cli.pb.go`, package `<pkg>cli`. Per service:

- **`Register<Service>Commands(root *cobra.Command, inv clisupport.Invoker)`** — mounts each
  annotated RPC at its `path`. Commands call through `Invoker`, so the tree is transport-agnostic:
  a CLI is a caller, and a caller does not pick the road.
- **`<Service>Coverage() clisupport.Coverage`** — covered, deliberately skipped, and unannotated
  procedures.

Each command gets a flag per scalar top-level request field (kebab-cased), positional arguments
from `args`, and `--request-json`. Fields no single token can carry — repeated, map, message — have
no flag; `--request-json` is how they stay reachable, and flags applied afterwards override it. Only
a flag the user actually typed touches the request. The response is printed as indented JSON
(through `encoding/json`, because protojson deliberately varies its own whitespace).

**Option: `require_annotation=true`** fails the build on any non-skipped RPC without a `(command)`
annotation.

> docs/08: *"a generated CLI that covers only 80% of RPCs may be worse than none."* The failure mode
> is not the gap, it is that the gap is invisible — a user cannot tell an unsupported operation from
> one nobody got round to annotating. Two answers, pick per repo: `Coverage()` makes the gap
> printable, and `require_annotation=true` makes it a build failure. An internal platform should
> require the annotation; a repo with a hand-written CLI over its important paths should not.

## Wiring

```yaml
plugins:
  - {local: bin/protoc-gen-bus, out: gen/go/bus, strategy: all}
  - {local: bin/protoc-gen-cli, out: gen/go/cli, strategy: all, opt: [require_annotation=true]}
```

## The five rules, as they apply here (docs/07)

1. **Guard on `Generate`.** Both plugins skip files that are only in the request as imports —
   `TestOnlyFilesToGenerate` asserts it against a request that carries `descriptor.proto`,
   `transports.proto` and `cli.proto`.
2. **`strategy: all`.** Neither plugin needs cross-file state today, but the ServiceDesc is a
   registry: keep the whole tree in one invocation so it can grow one.
3. **Sort before emitting.** Files by path, services and methods by name, flags by flag name,
   transports by enum value, imports by path. `TestDeterministic` generates twice and compares
   bytes.
4. **Fail, don't warn.** Streaming, an empty `on`, `TRANSPORT_UNSPECIFIED`, a `(command)` with no
   path, an `args` entry naming a field that does not exist or is not scalar, and — under
   `require_annotation=true` — a missing annotation, are all errors that name the file and line.
   Nothing is emitted for a file whose model did not validate.
5. **Deterministic headers.** `// Code generated by ... DO NOT EDIT.` and `// source: <path>`. No
   timestamps, no plugin version.

## Tests

`go test ./...`. The goldens are the committed Go under `testdata/gen/**/fixturev1{bus,cli}` —
real packages, not blobs, so `internal/gentest` imports them and proves the generated code
registers, dispatches, calls over the memory driver and runs as a command tree. (`go build ./...`
skips `testdata`; that importer is what type-checks the goldens.)

- Rewrite the goldens: `UPDATE_GOLDEN=1 go test ./...`
- Regenerate the fixture's message types after editing `testdata/proto`: `hack/genfixture.sh`
- Regenerate this module's own annotation types: `buf generate --template tools/buf.gen.yaml` from
  the repo root

The fixture's descriptors come from generated Go, which carries no `SourceCodeInfo`. Anything that
depends on it — doc comments, `file:line:col` in a refusal — is covered by synthesised descriptors
instead (`TestDocComments`, `TestStreamingRefused`), because the golden is blind there.

## Seams

**Core exports no `Registrar`.** `Register<Service>` therefore takes an anonymous interface. Naming
it in this module would make every service's runtime depend on `tools` (and so on cobra); naming it
per generated package would collide the moment two `.proto` files share a directory. The right home
is core, next to `Registry`:

```go
type Registrar interface {
    Register(sd *ServiceDesc, impl any, chain *ChainSpec) error
}
```
