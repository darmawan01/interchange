# ADR-0006 — A service-level transport default that a per-RPC annotation replaces

**Status:** Accepted
**Date:** 2026-08-30 · **Phase:** 2

## Context

`(transports)` is the annotation that decides which roads an RPC travels, and §08 left it as an
open question: per-RPC opt-in, or per-service? Per-RPC only is honest and unbearable — a
twenty-method service repeats the same three-line annotation twenty times, and boilerplate that
dense stops being read, which defeats the point of an annotation whose value is that a reviewer
sees it in the diff. Per-service only cannot express the exception, and the exceptions are the
interesting cases: the one bus-only RPC, the one internal cross-tenant RPC.

So both levels exist. The real question is what happens when both are present, and that question
has two plausible answers with very different review properties.

## Decision

Resolved during the build, when `protoc-gen-bus` had to compute the fan-out: a service-level
`(service_transports)` sets the default, and a per-RPC `(transports)` **replaces** it entirely —
including the competing-consumer group — rather than merging with it. A method with no annotation
anywhere gets `[RPC, REST]`, the two synchronous roads; a method reaches a broker only because
someone wrote it down.

An annotation that is present but names no road is an error, not a fall-through to the default.
`(transports) = { group: "x" }` has two readings — "only change the group" and "expose on nothing"
— and guessing between them is how an internal RPC ends up on a public bus. The resolved list is
sorted and deduped, so the generated bytes do not depend on the order someone happened to type.

## Consequences

One annotation answers "what does this expose". A reviewer reading a per-RPC `(transports)` does
not need to find the service-level one and compose the two in their head — which is exactly what a
merge would require, and the whole point of the annotation is that the answer is visible in the
diff rather than emergent.

The cost is that the group is replaced too. An RPC that wants the service's queue group *and* one
extra road has to restate the group, and forgetting to restate it silently drops the method out of
its competing-consumer group. That is the price of "read exactly one annotation"; the alternative
is a rule where some fields merge and others replace, which is worse to remember than either pure
rule.

The second cost is that adding a road to a service default does not reach the methods that
override it. A service moving onto MQTT has to revisit every method carrying its own annotation.

## Alternatives

**Merge the two lists (union).** Rejected: the effective fan-out of a method is then the union of
two annotations in two places, so no single line in the file answers the question, and *removing*
a road from a method becomes impossible without removing it from the service.

**Per-RPC only.** Rejected as boilerplate that stops being read.

**Per-service only.** Rejected: it cannot express the exception, and the exceptions are where the
security-relevant decisions live.

**Treat an empty `on:` as "inherit".** Rejected as the ambiguous reading above; it is an error
instead.

## Evidence

- `api/interchange/transport/v1/transports.proto` — `TransportOptions`, `ServiceTransportOptions`,
  and the comment stating the rule: "Per-RPC (transports) overrides it entirely -- it is a
  replacement, not a merge, so a reviewer reads one annotation rather than composing two".
- `tools/cmd/protoc-gen-bus/transports.go` — `resolve(svcOpt, mOpt)`: method wins whole, else
  service, else `defaultRoads = [RPC, REST]`; `normalize` sorts, dedupes, and rejects both an empty
  road list and `TRANSPORT_UNSPECIFIED`.
- `tools/cmd/protoc-gen-bus/bus_test.go` — `TestResolve` pins all six cases, including
  "method replaces service entirely" asserting `wantGroup: ""`; `TestResolvedTransports` reads the
  same behaviour off the *generated bytes* (`GetItem` inherits group `fixtures`, `PublishItem`
  replaces it with `publishers`, `Ping` gets the default roads).
- `dispatch.go` — `MethodDesc.Transports` and `Group` carry the resolved answer to runtime;
  `Registry.MethodsOn` is what a binding asks.
- `docs/08-decisions.md`, "Resolved by building it".
